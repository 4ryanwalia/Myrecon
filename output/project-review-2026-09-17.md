# MyRecon project review — 17 September 2026

MyRecon's biggest opportunity is to make each check reliable, understandable, and easy to act on. The project already contains enough useful capabilities to support a strong product: username discovery, email exposure checks, domain/DNS/IP investigation, QR analysis, password exposure, educational content, and monitoring. The next release should connect and strengthen those workflows.

This review covers the Android app's main screens, navigation, data services, persistence, background work, ads, theme, and tests; the website's search/result workflows; and the API, CLI, and repository setup. Findings come primarily from source inspection, targeted checks, and existing store screenshots. The store screenshots represent an older UI and were used only as supporting visual context. No current emulator or physical-device walkthrough was performed. This is not an exhaustive security audit or a production load test. Application source was not changed.

**The strongest parts should stay.** Streaming progress and cancellation, explicit unverified username matches, Android breach outcome types, source links, persistent cleanup choices, contextual notification permission requests, password hashing on the device, and the shared backend service layer for web/CLI are useful foundations. The distinctive visual style can remain while readability improves.

**Make completed work durable and navigation predictable.**

1. **Implement Android Back consistently.** History/detail/article screens use local flags and visible arrows, with no application back-stack handler. System Back therefore cannot follow the same internal hierarchy. Add routes or explicit Back handlers for detail → list → main screen, and verify predictive/system Back, rotation, and returning from an external browser. See [MainActivity](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/MainActivity.kt:273) and [HistoryScreen](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/screens/HistoryScreen.kt:59). The interaction consequence is inferred from code and still needs a device test.

2. **Save reports for every supported lookup.** Username and QR checks write history, but the simple email/domain/DNS/IP completion path and Deep Search do not offer equivalent persistence. History's wording overpromises. Save structured reports with tool, query, timestamp, source status, coverage, and findings. Provide Run again, Copy, Share, Delete, and Compare with previous check. Keep passwords out of report persistence. Existing history truncates report text to 6,000 characters, replaces previous runs for the same query, and caps entries at 20. A small report database is a better fit once comparison and filtering are supported. See [completion path](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/screens/LookupViewModel.kt:237) and [history storage](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/data/ReconStore.kt:455).

3. **Retain state per tool.** Selecting another lookup currently cancels the job, clears the query, and discards the displayed result. Preserve drafts/results separately, and offer useful transitions such as Domain → DNS → IP with the relevant value prefilled. See [selectTool](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/screens/LookupViewModel.kt:172).

4. **Prevent stale requests from changing a newer result.** Android avatar enrichment merges by platform into whichever sweep is currently displayed, without verifying its handle. The web request handler reads mutable `activeTool` after awaiting a response. Add request IDs, immutable request context, and cancellation/response guards. Test A then B with A finishing last. These races were identified statically, not reproduced on a device. See [avatar merge](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/screens/LookupViewModel.kt:436) and [web completion](/C:/Users/91966/OneDrive/Desktop/Recon-main/frontend/assets/js/app.js:916).

**Readability needs correction in the design tokens.** Calculated from the actual foreground/background colors, white text on the dark theme's cyan primary button is approximately **1.81:1**. Dark muted text on the dark surface is **2.89:1**, and light muted text on white is **2.56:1**. These color pairs are used for meaningful content, including small explanatory text. Use a dark foreground on cyan, strengthen muted text in both themes, and increase important body text where space permits. Evidence: [theme](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/theme/Theme.kt:58), [colors](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/theme/Color.kt:23), [type sizes](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ui/theme/Type.kt:43).

Use the [WCAG contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) as the readability benchmark: 4.5:1 for normal text and 3:1 for large text, with exceptions such as inactive controls. Verify TalkBack names, selection state, progress announcements, and large font layouts on a device. Android documents Compose's default semantics and automatic touch-target expansion; do not infer that a small visible icon necessarily has a small interactive target. [Android accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults).

**Support the product with a reproducible engineering workflow.** The Android directory and Gradle project are deliberately excluded from this repository, and `git ls-files app ...` returns no tracked Android source. Keep that boundary if it is intentional, but place the app in its own private versioned repository with reproducible builds and CI. Do not rely on the website repository to preserve Android changes. See [.gitignore](/C:/Users/91966/OneDrive/Desktop/Recon-main/.gitignore:32).

Separate deterministic unit tests from opt-in tests that contact live providers. Add focused coverage for unavailable/partial responses, alert opt-out, batches beyond the watch limit, stale requests, navigation, and saved-report completeness. Use mocked providers for CI and a separate source-health check for changing third-party services. Give Android/web/CLI a shared result contract even where the actual engines differ. For API caching, define policies for partial and unavailable responses explicitly instead of treating every top-level successful wrapper as a complete lookup.

Debug currently uses real ad units, while the physical-device test ID is still a TODO. Use test ad units in debug or complete the test-device configuration before ad interaction testing. See [build configuration](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/build.gradle.kts:35) and [test devices](/C:/Users/91966/OneDrive/Desktop/Recon-main/app/src/main/java/com/aryan/myrecon/ads/Ads.kt:50).

**Suggested delivery order:**

1. **Reliability release:** truthful source outcomes, watch opt-out and fair scheduling, request identity guards, accurate privacy/identity wording, and ad-failure recovery. Success means failures remain visibly incomplete, all accepted watches receive checks, and turning a feature off actually stops it.
2. **Usability release:** Android Back, saved reports across tools, retained per-tool state, QR copy/paste/import, contrast corrections, and removal of the unfinished Photo destination. Success means a user can complete a check, act on it, leave, and return to the same useful result.
3. **Product refinement:** job-based Home, concise result summaries, filters, ownership classification, comparison between scans, and optional monetization experiments. Test with a few first-time users completing three tasks without coaching: check an address, inspect a QR/link, and reopen a past result.

Measure task completion, time to a useful result, abandoned checks, successful follow-up actions, and false-positive feedback. If product telemetry is added, count workflow events without recording typed passwords, email addresses, handles, URLs, or report contents.
