Bluesky and AT Protocol OSINT: handles, DIDs and feeds

Bluesky separates human-readable handles from permanent Decentralized Identifiers (DIDs) under the Authenticated Transfer (AT) Protocol. Because a user can rename a handle or attach a custom domain without changing their underlying DID, MyRecon helps investigators check both public AppView XRPC responses and independent domain corroboration before connecting profiles.

MyRecon editorial · Updated 2026-11-26

Key takeaways

  • Resolve human handles to permanent did:plc or did:web identifiers
  • Filter author feeds by at://<did>/app.bsky.feed.post/ to exclude reposts
  • Corroborate custom domain handles via _atproto DNS TXT or .well-known checks

Handles versus immutable AT Protocol DIDs

In backend/modules/deep_search_sources.py, a Bluesky handle without a dot automatically appends .bsky.social, while custom domain handles pass through verbatim. Resolving the handle yields an immutable did:plc: or did:web: identifier, which stays fixed even if the account owner later changes their display name or public handle.

How public AppView XRPC resolution works

MyRecon queries the public Bluesky AppView at public.api.bsky.app via the XRPC method app.bsky.actor.getProfile with the normalized actor parameter. After verifying case-insensitive handle equality and a valid did: prefix, Deep Search optionally calls app.bsky.feed.getAuthorFeed with limit=10 to inspect recent authored posts.

Custom domain verification as corroboration evidence

When a Bluesky handle uses a custom domain, AT Protocol relies on DNS TXT records at _atproto.<domain> or an HTTPS file at /.well-known/atproto-did pointing to the exact DID. While deep_search_sources.py relies on the public AppView resolution, investigators can check those domain records directly as independent ownership corroboration.

Worked verification workflow and false-positive checks

Start by checking whether extracted bio links in declared fields point reciprocally back to a known website or GitHub profile. Confirm each post URL on bsky.app directly in a signed-out browser, and treat reposts or same-display-name accounts as unrelated unless corroborated.

Honest source limits and unavailable feeds

Public AppView queries never access private direct messages, muted lists, or accounts restricted from signed-out viewing. If getAuthorFeed hits a rate limit or timeout inside c.optional(), MyRecon preserves the confirmed profile while marking activity_available as False instead of erasing verified profile evidence.

Frequently asked questions

What happens if a Bluesky feed fails to load during lookup?

In deep_search_sources.py, getAuthorFeed runs inside c.optional(). If the feed endpoint times out or fails, MyRecon still returns the confirmed profile and sets activity_available to False.

How does AT Protocol verify a custom domain handle?

A domain owner publishes their exact DID in a _atproto.<domain> DNS TXT record or at https://<domain>/.well-known/atproto-did. Checking those records independently corroborates the handle shown by AppView.

Does MyRecon follow links listed in a Bluesky bio?

No. deep_search_sources.py extracts URLs from the profile description text into declared fields for analyst review without crawling external bio destinations.

Can public XRPC lookups read blocked or private Bluesky data?

No. Queries to public.api.bsky.app only inspect publicly accessible AppView records within a 14-second deadline and 2 MB response cap, and non-200 errors remain unresolved.
