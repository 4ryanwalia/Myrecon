Username search benchmark: findings, evidence and limitations

Updated 28 November 2026 · MyRecon editorial · How we check facts

In a recorded search for 4ryanwalia on 30 September 2026, MyRecon reported 12 hits, Sherlock 19 and Maigret 35. Reviewing the unique profile addresses supported 12, 11 and 10 leads respectively. On the 210 exact addresses checked by all three engines, the supported counts were 8, 9 and 9. Those two views answer different questions; neither establishes an overall accuracy ranking.

Published and reviewed: 1 November 2026 by MyRecon. This is a publisher-run study of our own product and competing tools. The September observations are historical; publishing this article did not rerun those scans. A separate daily control sample is dated below. A supported public profile is a research lead, not proof of ownership or username availability.

Did username search results change from day to day?

In 22 runs from 1 to 23 November 2026, inconclusive GitHub results appeared in one Sherlock run and two Maigret runs. Every affected GitHub control had a definitive result in other runs. A different pattern repeated on Hacker News: the benchmark’s Sherlock configuration reported all ten controls as claimed in every run, although the official API consistently returned no account for seven of them.

Sherlock’s four inconclusive GitHub results all occurred on 8 November. Maigret had six that day and ten on 19 November, when all ten returned HTTP 403. On GitLab, Maigret had one inconclusive result each on 5 and 7 November. Those observations suggest that trying again later can help resolve an inconclusive check. Repeating the Hacker News check alone would have repeated the same unsupported claims.

All 220 Sherlock Hacker News responses in this benchmark recorded HTTP 419 and the native verdict CLAIMED. MyRecon’s scoring accepted that verdict at the time, so the 154 disagreements count seven repeated controls, each observed 22 times. The normalized result now stays unknown on HTTP 419 in future benchmark runs, and the native verdict and status code are retained for review. The historical data below still shows what was recorded. The data does not identify which service or network layer generated those HTTP responses.

How to verify the 22 runs

The runs used the same ten handles on each of three platforms on GitHub Actions, with application caching bypassed. No qualifying run was recorded on 4 November. Each verdict was compared with the official API reference for the same control and run. The reference stayed consistent across all ten controls on each platform. The daily benchmark invokes the bundled Sherlock rules for the selected sites directly. In our separate eight-platform study, Sherlock’s captured upstream exclusions omitted Hacker News. These observations describe the selected benchmark configuration, pinned tool revisions and one execution environment.

Download the 660 paired observations as CSV or read the frozen JSON snapshot. The CSV uses fixture labels in place of handles. To reproduce the table, group by platform, count unknown as inconclusive and compare other verdicts with the reference. Group by fixture to distinguish repeated disagreements from distinct controls. See the pinned Sherlock and Maigret versions and the Hacker News API documentation.

How often did a username check give an inconclusive result?

On GitHub, a check based only on HTTP status gave an inconclusive result in 6 of 200 observations. On Hacker News, the same check was inconclusive in all 200. MyRecon recorded 20 runs from 1 through 21 November 2026. Each run checked the same ten handles on each service. The difference matters if you are deciding whether to spend time reviewing a possible match.

Does HTTP 200 prove that a username exists?

HTTP 200 tells you that the request succeeded. To verify an account, look for evidence identifying the exact username on the page or in a supported official response. In this sample, the GitLab status-only check recorded 80 responses with HTTP 200. In 20 of those observations, all repeats of one fixture, the API reference found no account.

The Hacker News public-page check recorded HTTP 419 for all 200 observations in the benchmark environment. The separate API reference returned 60 present and 140 absent observations. The data records the status seen by the benchmark client. It cannot establish what produced the 419 responses or how the page would respond on another network.

Download the 600 observations as CSV, published 22 November 2026. Group by platform and compare the two verdict columns. Count unknown in the HTTP status verdict column as inconclusive. A blank HTTP status means the check recorded no status code. Fixture IDs repeat within a platform and should be grouped together when counting distinct controls.

What the OSINTsearch preview exposed

The public OSINTsearch preview was observed at 15:35:44 UTC on 30 September 2026, with the user completing the CAPTCHA. It displayed 753 endpoints checked, 21 endpoint hits and 19 grouped matches. These are different units. It named 14 platforms and hid five matches; every profile URL was hidden. Those results cannot be scored as supported or contradicted, or placed in the shared-address comparison.

The named platforms were Instagram, GitHub, YouTube, Pinterest, Twitter (X), Reddit, Buy Me a Coffee, Periscope, HackerOne, Hacker News, Docker Hub, Product Hunt, VirusTotal and Replit. The displayed 15 seconds was the provider's timer, not an independently measured result. See the captured preview and the original query; the current service may differ from the capture.

Methodology and evidence rules

  1. Use one explicitly supplied public handle. Run the standard MyRecon catalogue, Sherlock with its recorded upstream exclusions, Maigret's enabled unprotected username catalogue, and the separately observed OSINTsearch free preview. No customer history, private content, credentials or breach data enter this case study.
  2. Keep native outcomes. Preserve positive native verdicts, duplicates, normalized unknown outcomes and HTTP status codes. A tool's reported hit remains visible even when HTTP-error normalization quarantines it.
  3. Review sources separately. Use typed official API account objects, explicit missing responses, a different account handle, or separately recorded profile identity and missing-control observations. HTTP 200, agreement between tools, a challenge and a login wall do not establish existence. Parking destinations contradict a public-profile lead, without establishing whether an account ever existed.
  4. Score only supported evidence. Classify each unique reported address as supported, contradicted or unverified. Keep duplicates separate. Contradicted counts are observed lower bounds on false positives, and unresolved results remain unresolved. Do not infer common ownership.
  5. Compare both scopes. Show each complete recorded run and the exact-address intersection. Keep the hidden preview results outside address-level scoring.

Corrections retained in the evidence

The initial MyRecon run reported 13 hits, with 12 supported leads and one contradicted lead: the requested RubyGems URL resolved to the fermion profile. A digit-prefixed path could be interpreted as a numeric account ID. An exact-handle check was added and the full engine rerun. The final RubyGems check remained ambiguous rather than being reported as a match. The original error remains in the recorded inputs.

A subsequent run before recovery reported 11 supported hits. General rules were added for exact active Buy Me a Coffee creator records, exact OpenStreetMap profile identity, and typed Reddit account objects. The final full run recovered Buy Me a Coffee, bringing the supported total to 12. OpenStreetMap passed a direct check but was blocked during the full run; Reddit was challenged locally. Those engine outcomes remain unknown even where a separate source review supports the profiles. The rules apply to arbitrary handles and do not use a saved result for this account.

Limitations and interpretation

  • Selection and publisher bias: one owner-requested handle and a small fixed control set do not represent all usernames, services or network conditions. MyRecon runs and publishes this comparison.
  • Missing truth and blocked checks: no contradicted reported leads is not a zero-error guarantee. Unknown engine outcomes can conceal missed profiles, and unverified leads may later be supported or contradicted.
  • Time and configuration: platform responses may change between scans and verification. Catalogue coverage, exclusions, endpoints, concurrency and overlapping local runs prevent a controlled speed ranking.
  • Corrections used this case: the final MyRecon run follows fixes informed by the observed handle mismatch and missing profiles. It is not an untouched, held-out evaluation. Earlier results are retained for review.
  • Hidden preview evidence: five OSINTsearch matches and all its profile URLs were hidden. No accuracy or identity inference is made for them.
  • Scope of a lead: a matching public handle does not confirm identity, common ownership, registration availability or access to private information.

Methodology review and limitations (28 November 2026)

A verification review on 28 November 2026 checked cross-section consistency between the 30 September case study, the 20-run HTTP status dataset (600 observations) and the 22-run repeatability dataset (660 observations). All observation counts, pinned commit hashes and CSV export definitions match across sections.

  • Repeated-measurement clustering: The 154 Sherlock Hacker News disagreements represent 7 distinct controls observed across 22 runs (7 x 22 = 154), and the 20 GitLab HTTP-200 contradictions represent 1 fixture observed across 20 runs (1 x 20 = 20). Analysts must group by fixture ID rather than treating repeated runs as independent handles.
  • Post-hoc rule fixes in the 30 September case: As documented in the Corrections section, the final MyRecon 12/12 supported count followed bug fixes made after inspecting earlier runs on 4ryanwalia. That makes the 30 September run a documented diagnostic case, not a blind out-of-sample benchmark; use the predeclared 1 November 35-control study for pre-registered controls.
  • Datacenter runner artifact: The 200/200 Hacker News HTTP 419 responses reflect GitHub Actions runner egress. Residential or mobile networks can receive different status codes on the exact same URLs.
  • Authorship and auditability: Written and reviewed by Aryan Walia (CEH, Founder) under our editorial method; HTTP semantics referenced against RFC 9110 (checked 28 November 2026).

Reproduce and inspect the evidence

Use Python 3.12 in an isolated environment and install Requests plus backend/tools/requirements-benchmark.txt. The requirements pin the third-party source revisions. Run the following from the repository root:

python backend/tools/username_benchmark.py --username 4ryanwalia --output-dir output/benchmark-4ryanwalia
python backend/tools/review_username_benchmark.py --username 4ryanwalia --output-dir output/benchmark-4ryanwalia
python backend/tools/review_profile_controls.py --username 4ryanwalia --output-dir output/benchmark-4ryanwalia
python backend/tools/build_username_benchmark.py --input-dir output/benchmark-4ryanwalia --output frontend/data/username-benchmark.json

The builder also needs the recorded auxiliary inputs: the OSINTsearch preview, earlier MyRecon runs, source-review observations and unfiltered Sherlock diagnostic. Save each top-level item using its corresponding JSON filename in the output directory. Preserve fresh measurements when rerunning engines. Reusing a recorded review preserves its original date and does not constitute fresh verification. No authentication, proxies, retries or block bypass were used in the recorded local comparison.

For the separate daily sample, run python backend/tools/daily_benchmark.py --require-named-tools after installing its dependencies; the recorded workflow documents the GitHub Actions environment. New runs may differ as services and exclusion lists change.
